This includes eliminating the need for customers to submit standard batch work and for Operations staff to release jobs based on job dependency. By use of the Automatic Recovery facility, to formulate recovery strategies for all failing applications, without Operator intervention, thus enabling a speedy and accurate resolution of problems.To ensure efficient utilisation of the CPU, its peripherals and the dependencies between jobs which will result in batch output being available, for the customer, on schedule.To ensure that, should failure occur on critical resources such as tape drives, cartridge drives or printers, the impact on batch throughput and customer schedules is minimised.To provide maximum visibility of application details and status to authorised controllers of that application. Conversely to ensure that unauthorised access to this information is prevented.WORKLOAD DEFINITION TWS schedules its workload according to internal Databases that control and define a concept of WHAT, WHEN and WHERE scenarios.The Application Description Database contains WHAT operations (jobs) are to be processed, the Calendar/Period Database describes WHEN they should be scheduled, and the Work Station Database defines WHERE the work will run.Before TWS can control your workload you must give it information on the environment that it will control. The tasks that you want TWS to perform like running jobs, are called 'operations' and these 'operations' are grouped together with other relevant information in order to construct a batch schedule, this batch schedule is called an Application.An TWS Application consists of one or more jobs, which are run together, in a standard run cycle.For each batch job, you define attributes to define when it is to be run, its run time, its dependencies and resources (reserved datasets etc).-see section on the Data collection processSome jobs may be dependent upon the successful completion of prior ones, so they are defined together as dependencies. TWS takes into account two kinds of dependencies, external ones (between applications)and internal ones (within an application).	THE DATA COLLECTION PROCESSFor each Business Application to run under TWS control,  information is required in order to build the databases, which describe detailed run-times and resource usage for each job.The 'STANDARD' run provides the basis for TWS scheduling, consisting of regular runs of batch at pre-determined intervals (periods).The following information is required to construct the Applications:-Application Jobnames (Standard and Non-Standard runs)Description - Brief description of jobOps Instrs - Operator instructions for recoveriesExclusive Datasets. Instructions must be available  before job implementation.EXCLUSIVE DATA-SET NAMESEach Jobname defined may use one or more 'special resources' in the system that are also used by jobs from other Applications. Such a resource could be a dataset needing exclusive use. The special resource subsection contains the name of the resource and whether it is required by the Jobname for shared or exclusive use.  By checking the special resource requirements of Jobnames in different Applications, TWS can correctly schedule these Applications if there are any potential conflicts or contentions. Special Resource flags are also utilised to control batch flow..JOB DURATIONFor each operation (jobname) defined within an Application, the estimated run time value is specified. This value is modified within the Application Database according to 'actual' measurements taken as TWS records and monitors actual job duration times.EXTERNAL PREDECESSORSA predecessor can be defined as an online system such as CICS or IMS, which needs to be shutdown before the suite is allowed to run.  Many Applications are dependent on the completion of jobs runningin external Applications under TWS. The name of a predecessor or successor application, together with the TWS job number of the relevant operation can be specified in order to set up a dependency 'network'between Applications.INTERNAL PREDECESSORSEach Jobname in an Application may have one or more dependencies, or predecessor , that must be completed before it can start. Internal dependencies, within the same Application are specified to enable correct sequencing of jobs. Parallel running can occur where 2 or more jobs are not dependent, enabling a faster turnaround of work.HIGHEST RETURN CODES (Job Completion Checking)When a Job finishes processing, TWS determines the conditions under which it ended by inspecting the return code of the Job. This is determined by the RETURN CODE keyword statement in the TWS installation procedures.WHEN TO RUNThe period cycle represents the day for submission of the Application  to the current plan..requirements as follows:-Sunday through to Saturday:-  (specify day)Daily, Weekly, Monthly etc.:- (specify cycle)Non cyclic (specific days):- (specify dates)The LONG TERM and CURRENT PLANLONG-TERM PLANThe Long-Term planning function plans production runs and enables Operations and Users to examine and analyse the expected future workload.The Long Term Plan can serve as a basis for documenting the Service Level Agreements. It enables you to relate Service Level Agreements directly to schedules, so that the User can see when and how their workwill be processed.The Long-Term Plan, generated by the long-term planning function, is a high-level schedule of processing activities for the forthcoming weeks and months.The Long-Term Plan lists, by day, the instances of applications to be run during the plan period. It shows when they are to be run, and the dependencies among different applications.The Long-Term Plan contains run time and external dependency information on a day-by-day basis for all TWS Applications within the time period specified by the Long-Term Plan existence. To create detailed schedules in the current plan, TWS takes the information about which application occurrences to schedule from the Long-Term Plan. The period covered by the Long-Term Plan varies per account and is extended accordingly once the period expires, via an TWS batch job.  CURRENT-PLANThe Current Plan is a detailed short-term work plan that includes the individual operations, together with their dependencies, planned start and end times, deadlines, priorities, and resource requirements.The Current Plan is the part of TWS that lets you see the status of the batch work. Through online displays you can request status information about particular jobs or groups of jobs. Information, such as current status, start and end times, and completion codes, can be displayed.The Current-Plan covers a period of 24 hours, which will bring in from the Long-Term plan all Applications with an input arrival time (IAT) that is within the specified period.The Current-Plan updating process is controlled by TWS batch jobs BATCH PROCESSINGHOW DOES THE BATCHWORK COME IN AND RUN EVERY DAY ??????The job schedules 'appear' every day after the current Plan update and start to process as defined, the arrival of these schedules is a result of the relationship between the Long Term Plan(LTP), the Current Plan(CP), the Calendar/Period Database, the Workstation Database and the Application Description Database (AD).When you create an application in the AD, it contains all the information on the jobs within that Application including when they are scheduled to run. This information is contained within the LTP for the time span specified for the current LTP. This information and any changes or additions to the LTP are picked up when the LTP is first created and by subsequent modifies and extensions to the LTP.In simple terms the Current Plan covers a section of the LTP but with expanded information on Work Station and operation data from the AD database. The Current Plan is the 'dynamic' part of TWS and as such is updated in  ‘real time’ by the TWS JES and SMF exits.The process each day is as follows:-Firstly, the LTP is modified by a batch job and this checks the AD database and Calendar/ Period descriptions for any additions or amendments and updates itself with these changes.Secondly, the CP is then extended by 24 hours and accesses the LTP to obtain the data on all the Applications scheduled to run within the next 24 hour period. The Current Plan is then created with ALL relevant information and dependency requirements resolved.																	TWS FUNCTIONS JOB COMPLETION CODESWhen the operation (batch job) ends, TWS determines the conditions under which it ended by inspecting the return code of the job. The job's return code is created by the event writer as either the highestreturn code of all executed steps in the job or the return code of the last step executed. This is determined by the return code keyword (RETCODE) on the event writer (EWTROPTS) statement. If the job's return code is larger than the value defined by the highest return code (HIGHRC) keyword in the TWS startup procedure, the job is treated as having ended in error.Before making this decision, however, TWS first checks the list of completion codes specified by the NOERROR keyword in the TWS startup procedure. If the completion code is found in this list, the job is treated as having ended normally.A completion code specified by the NOERROR keyword can be either global in the sense that it applies to all jobs, or it can  be specified to apply to a subset of all jobs or job steps within jobs. AUTOMATIC JOB RECOVERYThe automatic recovery function in TWS allows recovery strategies for Applications that have ended in error. The recovery criteria is specified in the JCL as a special control statement.The automatic recovery function gets control when a job ends in error, depending on the statements coded in the JCL of the job. During Auto Recovery the following information is utilised for recovery purposes.:-The abend code of a step that abendsThe return code of the step that failsAn error code set by TWSAn error code set by the Job Completion Checker function.NOTE: The subject of Auto Recovery is detailed in a later section of this Document. EVENT TRIGGERED TRACKING (ETT) and SPECIAL RESOURCESThe Event Trigger Tracking,(ETT) facility works by tracking external events happening outside of TWS that will have an effect on events within TWS.ETT uses  two  elements for its ‘triggering’ mechanism, namely Jobs and Special Resources.The required ‘triggering’ event is set up within the ETT database utilising either the Job or Special Resource functionA Job entering the JES reader, can be tracked and then trigger off the specified Application through TWS.A Special Resource ‘flag’ can be coded in the JCL of any job running on the system. This ‘flag’ when invoked will be detected by TWS and the triggering requirement actioned.Special Resources can also be utilised to control the batchwork flow within the Current Plan.  TWS  THE TWS MAIN MENU This is the TWS Primary Menu and from this panel you can select the following options:-Option 1: DATABASE	         Browse the Application DatabaseOption 2: LTP		         Browse the Long-Term-PlanOption 3: DAILY PLANING      NOT USEDOption 4: WORK STATIONS    Access to READY LIST and WORK STATIONSOption 5: MCP                             MODIFY /MANIPULATE Applications/Operations in the CP Option 6: QCP		         Browsing Applications and Operations in the CPOption 7: OLD OPERATIONS  NOT USEDOption 9: SERVICE FUNC        Deactivate job submission (Some options not available)! This can only come with experience, therefore some prior effort into ascertaining ‘batch windows ‘, criticality’s, SLA,s etc for ALL Applications running under their particular TWS system, should be given some consideration.Certain Jobs will run longer than normal or appear not to be running at all, so basic diagnosis of apparent problems can often alleviate potential adverse effects on batch throughput.Critical TWS ‘housekeeping’ and maintenance jobs should warrant extra vigilance and monitoring The concept of a ‘workload profile’ should be considered by Operations to assist monitoring batchflows as and when they occur, this should negate the need for generic searches on ALL batchflows. TWS has a function called the READY LIST, which allows you to monitor the batch, by utilisation of Extended status codes and dynamically control the batch via commands within the panel.However, its worth remembering that the READY LIST does NOT show Applications that are in WATING status, therefore it does not give you a ‘complete’ picture of your batch environment.As previously stated, there are many methods to monitor the work, so its best practice to utilise other panels within TWS as well.A combination of the following options will cover most of the monitoring and activity requirements.READY LIST (option 4.1)MODIFY the CURRENT PLAN (options 5.2 / 5.3)QUERY THE STATUS OF WORK IN PROGRESS (options 6.3 / 6.4) The following pages within this document will show examples of each of the above methods.TWS has many duplications in its functionality, therefore there are no ‘hard and fast’ rules on monitoring through TWS, so try out all the defined Options and find the best method for you.  THE READY LIST All operations in the current plan are associated with a workstation, you can use the TWS dialogs to display the operations.  For an overall view, you use the Query Current Plan dialog However, if you want to find out which operations are due to start or are currently started at a, particular workstation, you should view the workstation READY LIST. The ready list contains operations that have no outstanding predecessors and it also contains operations defined to the workstation that are waiting for a particular event. Therefore the READY LIST can display:-Operations waiting for a particular time or resourceOperations which have already startedOperations that have ended in errorOperations on the JES queueThe ready list contains operations that have no outstanding predecessors operations defined to the workstation that are waiting for a particular time or resource, operations that have already started, and operations that have ended in error.  The status codes of operations in the ready list can be:A -  Arriving--ready for processing; no predecessors were defined.I  - Interrupted.R -  Ready for processing; all predecessors are complete.*  -  Ready--at least one predecessor is defined on a non-reporting workstation; all others are met. S  - Started.E  -   Ended-in-error. These are some of the tasks you can perform using the ready list:    - Diagnosing delays.     - Setting the status of an operation.    - Resetting an operation to its previous state    - Interrupting an operation.      - Reporting an operation as ended-in-error.      - Viewing operator instructions.      - Preparing JCL at a setup workstation.      - Delaying an operation, and releasing it.      - Removing an operation from the current plan, and restoring it.      - Running an operation immediately with EXECUTE.  You access the READY LIST via the WORK STATION option (4.1)USING THE READY LIST After taking option 4 from the main TWS menu, the above panel is displayed, from this panel you can set up your own READY LIST and customise it, or use the system default one.Option 1 takes you into the READY LISTS already created and Option 9 will take you into the panels to create your own version.The other options on this panel are not widely utilised, other than Option 4 (Work Stations) Within this panel you specify the Work Station that your batchwork is running on and also the Layout id.
